# 数字人口播模式讨论总结

日期：2026-06-27

## 背景

本次讨论围绕 `MediaCrawler-GUI` 后续的视频创作方向展开，重点是：

- 论坛用户建议不要强行做 PPT 原生动画复刻。
- 讨论“线稿动画”“数字人口播”“HF 动画层”“文章图片 assets”的产品化方向。
- 目标是在现有“快速模式 / 专家模式”基础上，增加更适合短视频平台的一键创作能力。

## 对论坛建议的判断

论坛用户提到：

- PPT 演示动画容易限流。
- 抖音可能抽帧判断低质内容。
- 单纯 AI 生成内容容易低质、同质化。
- 口播视频或其他真实视频素材更容易获得流量。
- 手绘线稿动画可能比普通 PPT 动画更自然。

我们的判断：

- 大方向基本对：平台确实不喜欢低质、重复、批量、模板化内容。
- 但他说得过于绝对：不是 PPT 动画天然没流量，也不是线稿动画一定不会被判低质。
- 更准确的产品判断是：不要做“PPT 录屏感”的视频，而要把内容重构成短视频表达。

## 线稿动画的含义

线稿动画可以理解为：

> 把内容变成线条、轮廓、手绘风格，再用描边、逐字、箭头等方式让内容像被画出来一样出现。

适合：

- 流程图
- 知识讲解
- 产品说明
- 教程拆解
- 图文内容转视频

但它不是当前最优先方向，只是后续可作为 HF 动画风格之一。

## 第三种模式：数字人口播模式

用户澄清后的设想是：

> 在当前快速模式 / 专家模式之外，新增一个模式。流程仍然是输入文字、GitHub 链接或提示词，一键生成“全屏数字人口播 + 少量 HF 动画 + 强调字幕”的短视频。

我们确认这个方向可行，而且比“PPT 转线稿动画”更适合做一键创作。

建议模式名：

- 口播模式
- 数字人口播
- 一键口播

更推荐产品名：

> 口播模式

因为“数字人”只是能力之一，未来也可以扩展为真人口播、纯配音口播或虚拟主播。

## 口播模式的画面结构

核心画面不是：

```text
PPT 背景 + 右下角数字人
```

而是：

```text
全屏数字人 / 口播人物
+ 巨大关键词
+ 强调字幕
+ 列表动画
+ 少量文章图片 / GitHub 信息卡
```

推荐图层结构：

```text
底层：全屏数字人口播视频
中层：关键词大字 / 列表 / 来源图片 / 信息卡
上层：字幕 / 强调词 / 标签
音频：数字人口播 + 背景音乐
```

重要结论：

- 数字人占满全屏时，不需要透明蒙版。
- HF 不负责主体人物视频。
- HF 只负责关键点动画、列表出现、强调字幕、来源图片入场、信息卡等轻量动效。

## 用户提供图片后的对齐

用户提供的抖音截图参考画面是：

- 主体人物占据画面中心。
- 巨大关键词围绕人物出现。
- 底部有字幕。
- 内容更像口播短视频，不像 PPT 翻页。

我们确认设想一致，但需要强调：

> 不只是“小卡片浮层”，口播模式应支持大字冲击效果。

例如：

```text
人物在中间
左侧出现“自动采集”
右侧出现“数据分析”
底部显示逐句字幕
```

或者：

```text
人物后方/两侧出现巨大关键词
关键词跟随口播节奏放大、入场、消失
```

## 文章图片 assets 的公共能力

用户提出：

> 把文章图片下载成 assets 并自动用于视频画面，快速模式也要有，然后口播模式复用。

我们确认这是对的。

这个能力不应该做成口播模式专属，而应该做成公共来源素材能力：

```text
输入文章链接 / GitHub 链接 / 提示词
-> sourceFetch 读取来源
-> 从 markdown 提取图片 URL
-> 下载到 workflow assets
-> 生成 asset_context
-> 快速模式、专家模式、口播模式都可复用
```

## 快速模式如何使用文章图片

快速模式没有数字人时，可以把文章图片用于：

- 开头视觉冲击
- 图文动效场景
- 案例展示
- 对比图
- 重点内容证明

但不要做纯图片轮播。

推荐混合：

```text
文章图片
+ 文字摘要
+ 数据卡
+ 关键词
+ 高亮框
+ 转场
```

## 口播模式如何使用文章图片

口播模式里，文章图片是辅助材料，不应该长期占屏。

推荐方式：

```text
数字人讲到某个观点
-> 右侧/左侧弹出文章图片
-> 2-5 秒后收起
-> 同步出现关键词或列表
```

例如：

```text
数字人：这个项目最核心的是自动采集能力
画面：左侧出现“自动采集”大字

数字人：文章里提到它支持多平台内容抓取
画面：右侧弹出文章图片或截图

数字人：它适合做运营分析和素材管理
画面：出现列表：运营分析 / 素材管理 / 自动化采集
```

## 对 hyperframes-fix 仓库的分析

查看了仓库：

> https://github.com/liangdabiao/hyperframes-fix

远端 `HEAD`：

```text
e54dcfcf86574e9dde543ed99cccd43aa77a2607
```

结论：

- 它不是完整应用，主要是 HyperFrames skill / reference 文档补丁。
- 它确实描述了微信公众号文章转视频流程。
- 它的文章图片提取逻辑主要是从 Markdown 里提取 `![alt](url)`。
- 它还提供了 Pexels 背景图工作流。
- 没看到完整的“任意网页自动截图作为素材”的实现。
- 它提到的截图更多是 HyperFrames 渲染/质检截图，或浏览器录制生成视频，不是通用网页截图。

它的核心文章流程：

```text
微信公众号链接
-> 调 ideaflow-article-to-markdown.hf.space 转 Markdown
-> 从 Markdown 提取图片
-> 下载图片
-> 生成 showcase / infographic / comparison / quote 等场景
-> TTS
-> HyperFrames HTML 视频
```

最值得借鉴的点：

- 从 Markdown 提取图片 URL。
- 下载图片并作为视频素材。
- 文章图片用 `object-fit: contain`，不要裁切。
- 不做纯图片轮播，要混合文字、数据卡、引用、对比等场景。

## 当前项目已有基础

当前项目已经有：

1. 外部来源读取能力  
   文件：`server/services/sourceFetch.js`

   已支持：

   - 普通文章正文提取
   - 微信公众号正文容器识别：`js_content` / `rich_media_content`
   - HTML `<img>` 转 Markdown 图片语法
   - GitHub 仓库 README、语言、Star、目录结构读取

2. Playwright HTML 视频渲染能力  
   文件：`server/services/creative-video/html-video/hyperframesPlaywrightAdapter.js`

   已支持：

   - 打开 HTML 动画页面
   - Playwright Chromium 录制 WebM
   - ffmpeg 编码 MP4

3. html-video assets 基础目录能力  
   文件：`server/services/creative-video/html-video/assetStore.js`

   已有：

   - `ensureAssetDir`
   - `resolveAssetPath`
   - assets 路径安全校验

当前缺口：

```text
sourceFetch.markdown 里有图片引用
但还没有自动下载成 workflow assets
也还没有形成可供视频规划复用的 asset_context
```

代码中已有提示：

```text
图片素材将在下一阶段开放。
```

相关文件：

- `server/services/creativeContext.js`
- `server/services/creativeWorkflows.js`

## 建议的最小实现顺序

第一阶段，只做公共文章图片 assets：

```text
1. 从 sourceFetch 返回的 markdown 提取 ![alt](url)
2. 过滤非 http(s)、重复 URL、明显无效 URL
3. 下载前 6 张图片到 workflow assets 目录
4. 生成 asset_context.assets
5. 快速模式和口播模式都读取这批 assets
```

暂时跳过：

- 任意网页自动截图
- 复杂图片理解
- 图片 OCR
- 图片和口播语义精确匹配
- 大规模素材库

第二阶段，快速模式使用 assets：

```text
文章图 -> showcase 场景 / 背景 / 对比图
```

第三阶段，口播模式复用 assets：

```text
全屏数字人
+ 大字关键词
+ 强调字幕
+ 文章图片短暂浮层
+ GitHub 信息卡
```

第四阶段，再考虑自动截图：

```text
GitHub 仓库首页截图
公开文章首屏截图
```

自动截图要作为增强能力，失败不阻塞视频生成。

## 自动截图的判断

现在不建议优先做任意网页截图。

原因：

- 网站登录、反爬、懒加载不可控。
- 微信文章图片和页面结构复杂。
- 截图容易包含广告、导航、弹窗。
- 截图文字在视频里可能太小。
- 任意 URL 截图要继续处理 SSRF/内网访问风险。
- 还要裁剪正文区域，否则画面脏。

如果后续要做，建议只做两个明确场景：

```text
1. GitHub 仓库首页截图
2. 公开文章首屏截图
```

## 推荐产品定义

新增第三模式：

> 用户输入文字、GitHub 链接或提示词，系统自动生成一条全屏数字人口播视频，并在讲到关键点时自动弹出关键词、列表动画、强调字幕和来源图片。

公共素材增强：

> 当输入是文章链接时，系统自动提取正文和文章图片，把图片保存为 assets，供快速模式、专家模式和口播模式复用。

## 最终共识

当前最值得做的不是 PPT 动画复刻，也不是任意网页截图，而是：

```text
公共文章图片 assets 管线
+ 快速模式图文动效复用
+ 口播模式数字人视频复用
+ HF 负责轻量关键词/列表/字幕/图片入场动画
```

最小、稳定、可落地的版本：

```text
文章链接
-> 读取正文
-> 提取并下载文章图片
-> 生成口播脚本
-> 数字人全屏讲解
-> 大字关键词 + 字幕 + 少量图片浮层
-> 导出短视频
```
